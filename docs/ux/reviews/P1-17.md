## Matches the spec

**The type roles against `design/tokens.json` → "Display (Hindi)"** (all in `MemixType.kt`):

| Role | Token (Hindi) | Code | |
| --- | --- | --- | --- |
| `display-xl` | Teko 40 / 60, 700, spacing 0 | `hindiDisplay(face, 40.sp, 60.sp)`, `FontWeight.Bold`, no `letterSpacing` set (unspecified is 0) | match |
| `display` | Teko 28 / 44, 700, spacing 0 | `hindiDisplay(face, 28.sp, 44.sp)` | match |
| `wordmark` | Anton 28 / 30, 400, every language | `wordmark = antonDisplay` (the same style as English `display`) | match |
| Other four languages | Anton 40/44 and 28/30, 400 | the `else` branch is the old styles, unchanged | match |
| Interface roles | Space Grotesk, system Devanagari | untouched | match |

- **The switch follows the app language, not the characters.** `usesHindiDisplayFace()` reads `LocalLocale.current.language == "hi"`, the same source `DisplayText` already uses for `toUpperCase`. One string never mixes two display faces, as the spec says (Latin words in a Hindi headline are set in Teko too).
- **Loaded only in Hindi.** The `Font(Res.font.teko_bold)` call sits behind the `if`, so the other four languages never read the file.
- **Language change.** `MainActivity` has no `configChanges`, so a per-app language change recreates the activity and the type is rebuilt from the new locale. The spec's "follows on the next composition, no restart" holds trivially on Android.
- **Wordmark.** `HomeScreen.kt:104` uses `MemixTheme.type.wordmark`; the string `wordmark` is "Memix" in one `values/strings.xml` only, so it is never translated. The debug long-press stays on it. The catalog lists "Memix (wordmark)" and shows two Hindi samples, "मीम बनाएं (display-xl)" and "वीडियो मीम (display)", only when `usesHindiDisplayFace()` (request 4).
- **Every display use is covered.** Callers of `DisplayText` or `type.display` and `type.displayXl`:

  | Use | File | Style |
  | --- | --- | --- |
  | Home hero (`heading()` kept) | `HomeScreen.kt:72` | `displayXl` |
  | Entry-card titles | `EntryCard.kt:56` | `display` |
  | Create sheet hero | `Sheet.kt:229` (`heroTitle`), `CreateSheet.kt:50` | `display` |
  | Create sheet's two editor rows | `CreateSheet.kt:77` | `display` |
  | Export sheet hero | `ExportSheet.kt:82` (`heroTitle`) | `display` |
  | Export screen heading (`heading()` kept) | `ExportScreen.kt:260` | `display` |
  | Empty-state headlines (Drafts, Sounds, Templates, placeholders) | `EmptyState.kt:30` | `displayXl` |

  Nothing else uses Anton for chrome in Hindi: `memeCaption` has no caller except the debug catalog, and the captions in the editor are content (P1-10). The Create rows, the Export hero and the Export heading are new to the doc's "where it applies" list; DESIGN_SYSTEM now names them (see Fixed on my side).
- **Font file and license.** `teko_bold.ttf` is bundled once, in `:core:designsystem`; `CaptionCatalog` points Classic's Devanagari fallback at the same file name and `CaptionFonts.kt` reuses the resource, so there is one copy (request 5). `licenses/README.md` records Teko Bold 2.000, the googlefonts/teko commit `2bf909d…`, 257,136 bytes (251 KiB, the "251 KB" in the tokens) and the SHA-256. `Teko-OFL.txt` is the project's own OFL 1.1 with "Copyright 2023 The Teko Project Authors" and no Reserved Font Name, as the spec says. OFL 1.1 allows bundling in an app as long as the font isn't sold by itself and the license text travels with it (Guidance, the license text itself); the credits screen (P5-07, PRD line 263) is where it becomes visible to users (polish P3).
- **Contrast** is unchanged: same colors. `on-primary` on `primary` (the Video card's title) 7.9:1, `text` on `canvas` 16.9:1 (from the design changelog). Teko Bold at 28 sp and up is large text, so 3:1 would be enough anyway.
- **Spoken text** unchanged: the Home hero and the Export heading keep `heading()`, the Sheet keeps `paneTitle`, and a font change adds no semantics.
- **v2 rules:** no color, outline, shadow or gradient added; letter spacing 0 on the Hindi roles protects the headline bar (shirorekha), which tracking would open.

**The computed 200% fit at 360 dp** (Assumption: I have no Teko metrics here, so I take about 0.45 em per Devanagari syllable cell, and I use linear scaling, which is the worst case; Android 14 and later scale large sizes less than linearly ([Android 14 features, font scaling up to 200%](https://developer.android.com/about/versions/14/features))):
- **Hero** "मीम बनाएं": 5 cells at 80 sp is about 180 dp plus a space of about 20 dp, which is under the 328 dp inside the gutters, so it should stay on one line, 120 dp tall (60 sp at 200%, doubled). The scrolling Home column absorbs the extra height.
- **Entry cards** (inner width (360 − 32 − 12) ÷ 2 − 32 = 126 dp): "वीडियो मीम" is about 140 dp at 56 sp, so it wraps to two lines, each word alone, and every single word is under 126 dp. The title block is 2 × 88 = 176 dp, the card grows past its 4:5 minimum (the Row uses `IntrinsicSize.Min`), and the title sits above 16 dp of bottom padding, so the rounded clip never touches a mark. Nothing truncates: `DisplayText` has no `maxLines`.
- **Line height:** 60 and 44 are the engineer's measure of Teko's own spacing (1.433 em × 40 = 57.3, × 28 = 40.1, rounded up to the 4 dp grid), with `Trim.None` and `Alignment.Center`, so the extra 2.7 and 3.9 sp split evenly above and below and no mark is cut. I have not measured Teko's metrics myself (Assumption; the device frames decide).

## Polish

**P1. The first Hindi frame decides whether the locale source works (device check).**
- **Where:** `MemixType.kt` → `usesHindiDisplayFace()` (`LocalLocale.current.language`), also read by `CaptionFonts.kt` and the catalog.
- **The problem:** the whole ticket hangs on one call. I could not confirm from here that Compose Multiplatform's `LocalLocale` follows the per-app language on Android (`adb shell cmd locale set-app-locales`) and the system language on iOS. The Kotlin docs say each platform handles locale settings differently and recommend a platform entry point when the common API isn't enough ([Compose Multiplatform: resource environment](https://kotlinlang.org/docs/multiplatform/compose-resource-environment.html), Guidance). The strings come from the resource environment, which does follow the app language, so a mismatch would show Hindi words in the system face. The code compiles and `DisplayText`'s `toUpperCase` already depends on the same value, so I expect it works (Assumption).
- **Pass or fail:** `home-hi-100` shows the hero and card titles in Teko (tall, condensed, square, heavy), not the thin rounded system Devanagari of `docs/ux/reviews/P0-05/android-home-hi-200.png`.
- **If it fails** (this becomes a must-fix): read the language from the same place the string resources use, through an `expect`/`actual` value in `:core:designsystem` (Android: `LocalConfiguration`/resources locale; iOS: the preferred language the app resolved to), and use it in `usesHindiDisplayFace()` only. No other file changes; the property names stay.
- **Spec line:** What changes → "The switch follows the app language"; States → "Language switched while the app runs".

**P2. The Teko size factor for captions (P1-10) is not a P1-17 item, and applying it needs code (heads-up for the engineer and the PM).**
- **What it is:** inside a Classic caption the Latin text is Anton and the Devanagari is Teko Bold by per-cluster fallback (`CaptionCatalog.kt:12`, `AndroidCaptionRenderer` with `Typeface.CustomFallbackBuilder` and `setUseLineSpacingFromFallbacks(true)`). Teko's size relative to Anton there is `caption.geometry.devanagariSizeFactorUnderClassic`, **provisional 1.0** in both token files (lines 684 and 685). It is **set at phase-end QA, before the Phase 1 gate**, from the `mixed-scripts-anton` screenshot: Anton's cap height ("B") ÷ Teko's headline height (the शिरोरेखा over "ज") on one line; within 5% keep 1.0, otherwise the ratio rounded to 0.05. The procedure and the reason for the deadline are in **`docs/ux/reviews/P1-10.md` → Decisions on the engineer's known limits, item 5** (the P1-10 spec's Fonts section carries it too). The screenshot goes in `docs/ux/reviews/P1-10/` (`mixed-scripts-anton`), not in P1-17's folder.
- **It does not touch P1-17.** The display roles are fixed by the tokens (40/60, 28/44); no factor applies to them.
- **The cost to know now:** no Kotlin reads that token yet (no reference to `devanagariSizeFactor` anywhere), and a paint can't scale only the fallback font's glyphs. A factor other than 1.0 means a size span on each Devanagari run in the `StaticLayout` (for example `RelativeSizeSpan`), which has to be measured and drawn the same in the preview, the stand-in and the export. A result within 5% avoids all of that, so the QA screenshot should be taken early.
- **Spec line:** P1-10 → Fonts.

**P3. Teko must appear on the credits screen.**
- **Where:** P5-07 (credits and licenses), PRD line 263.
- **The problem:** the repo carries the license, but the app's own copy of it is the credits screen. Teko was added after P0-04's three fonts, so a list copied from the P0-04 files would miss it, and so would the four P1-10 caption fonts.
- **Fix:** when P5-07 is built, read the list from `core/designsystem/licenses/README.md`, which has the file, the source and the license for each of the eight font families.
- **Spec line:** none (a note for the PM when P5-07 is checked ready).

## Fixed on my side

- **Letter spacing in the tokens didn't match the code.** `design/tokens.json` and `design/system/tokens.json` gave `display-xl`, `display` and `wordmark` `0.01em` and `caption` `0.02em`, but `MemixType` has never applied any tracking to them (so the claim "the other four languages are unchanged" was true of the code and not of the token file). Set all four to `0`: the difference is 0.4 px at 40 px, the look that shipped and was reviewed from P0-05 on is untracked, and Hindi needs 0. No Kotlin change. Logged in `docs/ux/CHANGELOG.md`.
- **DESIGN_SYSTEM → Hindi display face → Where it applies** now lists every `DisplayText` use (the Create sheet's hero and editor rows, the Export sheet hero, the Export screen heading, empty states) and links this review.
- **The P1-17 spec** has a Status line (built, requests done, links to this review and to the P1-10 factor), and QA compares 6 (the Export hero and the nukta words).

## Notes (no change needed)

- **The Create sheet's editor rows grow by about 4 dp in Hindi** (44 sp line + 16 sp label + 32 dp padding = 92 dp against the 88 dp minimum). Both rows grow together; nothing clips.
- **The Home column is about 16 dp taller in Hindi** (the hero line is 60, not 44). It is centered and scrolls, so there is no layout shift to guard.
- **The Hindi words with a nukta ("फ़ोटो", "ड्राफ़्ट") and the conjunct in "ड्राफ़्ट"** are the shaping test for Teko (`docs/ux/specs/P1-17-hindi-display-face.md` → QA compares 6). I expect Teko, a full Devanagari design with 1090 glyphs, to shape them correctly (Evidence: DESIGN_SYSTEM → Hindi display face, from the google/fonts metadata; not seen on a screen).
- **`memixType()` builds its font family and styles on every composition of `MemixTheme`.** It's a cheap object, `MemixTheme` rarely recomposes, and it was already that way in P0-04. Not a P1-17 item; the principal mobile engineer's call.
