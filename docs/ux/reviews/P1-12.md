## Must fix before end-of-phase QA

**M1. At large font the Exported, Exporting and failure screens clip their buttons, and the result can shrink to nothing.**
- **Where:** `feature/export/.../ExportScreen.kt` → `ExportScreen` (the `Column` inside `AnimatedContent`), `Exporting`, `Exported`, `Failed`.
- **The problem:**
  - None of the three screens scrolls as a whole. The Exported tail (status, Share, footer) scrolls on its own but is measured first, so when it doesn't fit, the result gets 0 height. The spec says the result keeps **at least 40% of the screen height**, then the screen scrolls (Accessibility → 200% font).
  - Exporting and failure are plain Columns. Computed from the type sizes (display 28/44 in Hindi, body 15/22, button text 15 sp), Hindi at 200% on 360 × 640 needs about 570 dp for Exporting where about 548 dp is left, and about 700 dp for the failure state (two-line title, a five-line message, two 80 dp buttons). The last button, **Cancel** or **Back to editor**, falls below the edge with nothing to scroll. System back still leaves, but the visible control is missing (SC 1.4.4, 1.4.10 and the spec's "nothing cut").
- **Fix:** give each of the three screens the same shape. The picture area keeps a minimum share of the **screen** height and the whole screen scrolls below that:
  ```kotlin
  BoxWithConstraints(Modifier.fillMaxSize()) {
      val screen = maxHeight                       // the screen, not the content area
      Column(Modifier.fillMaxWidth().verticalScroll(rememberScrollState())) {
          Column(Modifier.fillMaxWidth().heightIn(min = screen), verticalArrangement = Arrangement.spacedBy(MemixSpacing.space4)) {
              // title / title row
              Box(Modifier.weight(1f).heightIn(min = screen * 0.4f)) { /* result or frame */ }   // 0.3f on Exporting and the failure state
              // the rest, no inner verticalScroll
          }
      }
  }
  ```
  With `heightIn(min = screen)` and an unbounded maximum, Compose sizes the weighted child to the minimum, so at 100% font the picture still fills the middle exactly as today. Remove the tail's own `verticalScroll` in `Exported`. The floors are 40% on Exported (spec) and 30% on Exporting and the failure state (new, in the spec now). Keep each screen's focus requester and live regions as they are.
- **Check:** Hindi at 200% on 360 × 640 (`adb shell settings put system font_scale 2.0`): on each of the three screens the last button can be scrolled fully into view; Exported keeps a result of at least 256 dp. At 100% nothing moves.
- **Spec line:** Layout → Exporting screen (Large font), Exported screen (Large font); Accessibility → 200% font.

**M2. Free up space asks Android for the wrong amount, so it can open a screen that says there is nothing to free.**
- **Where:** `feature/video-editor/.../export/ExportSheet.kt` → `Notices` (`onFreeUpSpace(shortBytes)`) with `ExportSheetControl.show`; `feature/export/.../ExportViewModel.kt` → `showFailure`; `composeApp/.../App.kt` → `ExportDestination` (`freeUpSpace.launch(EXPORT_HEADROOM_BYTES)`).
- **The problem:** `FreeUpSpaceLauncher.launch` puts its number into `StorageManager.EXTRA_REQUESTED_BYTES`, which Android defines as the **total** size an app wants to be able to allocate, not an extra amount. P1-02's import passes its total (`neededBytes`). The sheet passes the **missing** amount, so with 300 MB free and 600 MB needed it asks for 300 MB, which is already available. The failure state passes the flat 100 MB headroom, which is nearly always already free after the partial file is deleted. In both cases the system can answer "nothing to do", and the user who tapped Free up space is back where they started.
- **Fix:**
  - The notice keeps **showing** the missing amount ("Free up about 240 MB"), unchanged.
  - Sheet: add `spaceNeededBytes` to `ExportSheetUi` (the value `ExportSheetControl.show` already computes with `exportSpaceNeededBytes(estimate, writesStraightToGallery)`) and call `onFreeUpSpace(sheet.spaceNeededBytes)`.
  - Failure: in `ExportViewModel.showFailure` compute the same needed total for `job.choice` and `job.project` (`estimateExport` + `exportSpaceNeededBytes`), keep it in `ExportPhase.Failed`, make `ExportScreen`'s `onFreeUpSpace` a `(Long) -> Unit`, and pass the total from `App.kt` instead of `EXPORT_HEADROOM_BYTES`.
- **Check:** with the emulator's storage nearly full, the sheet's notice shows the missing amount and the system storage screen opens asking for the needed total; after a mid-export out-of-space failure, the same.
- **Spec line:** Settings rules → Free space (the new bullet "What the button asks the storage screen for").

**M3. Export covers the ratio pill at large font in Spanish and Portuguese, and touches it in Indonesian and Hindi.**
- **Where:** `feature/video-editor/.../VideoEditorScreen.kt` → `TopBar` (a `Box` with `align` for the three items).
- **The problem:** the Button has `space-5` side padding and a 15 sp label. Computed with Space Grotesk at about 0.55 em per character, "Exportar" at 200% is about 170 dp wide, so Export starts near x = 182 on a 360 dp screen. The centered pill ("9:16" in 12 sp Space Mono at 200%, plus its padding) spans about 139 to 221, so about 40 dp of the pill is covered. Ekspor (about 140 dp) and Hindi "एक्सपोर्ट" (about 130 dp) end within a few dp of the pill. Around 150% the es and pt labels already touch it. P1-11's renders were made before Export existed, so nothing has shown this yet. This is SC 1.4.4 (content lost at 200%); the pill is the user's only route to Canvas.
- **Fix:** replace the three `align`s with a small custom `Layout` that measures Close, Export and the pill, places Close and Export at the edges, and places the pill at the true center clamped so it clears both neighbors by `space-2` (`x = (width - pill) / 2` limited to `[closeRight + space-2, exportLeft - space-2 - pill]`). At 100% font it stays exactly centered, as P1-11 shows. Close and Export never shrink or lose their text. It fits at 360 dp even at 200% in every language (Close 56 + Export about 170 + pill about 82 = about 310 of 344).
- **Check:** Spanish and Portuguese at 200% font and at 150%: the pill is fully visible and tappable beside Export; at 100% it is centered.
- **Spec line:** Layout → Export button (At large font).

**M4. Hidden notices leave 48 dp of empty space under the facts line, which can push the sheet into scrolling at 360 × 640.**
- **Where:** `feature/video-editor/.../export/ExportSheet.kt` → `ExportSheet` (the middle `Column`, `verticalArrangement = spacedBy(space4)`) and `Notices` / `Notice`.
- **The problem:** `Notices` emits three `AnimatedVisibility` nodes as direct children of that Column. A hidden `AnimatedVisibility` is still a zero-size child, and `spacedBy` puts a gap between **every** pair of children, so three hidden notices add three `space-4` gaps (48 dp) of blank space between the facts line and Export video, and the gap changes as notices appear. Computed sheet height at 360 × 640, 100% font, with the watermark row and one notice: about 620 dp against about 616 dp available, so the sheet scrolls where the spec says it doesn't; without the dead gaps it is about 572 dp. (Estimate; the watermark row is P1-13's.)
- **Fix:** put the facts line and the three notices in one inner `Column` with no `spacedBy`, and give each notice's content `Modifier.padding(top = MemixSpacing.space4)` inside its `AnimatedVisibility`, so a hidden notice takes no space and a visible one brings its own gap. The Free up space Quiet button keeps its `space-1` gap.
- **Check:** the sheet at 360 × 640 with no notice, then with the not-enough-space notice: the gap above Export video is the same `space-4` either way, and the sheet doesn't scroll at 100% font.
- **Spec line:** Layout → Export sheet (Spacing).

**P2. Three spoken-name problems on the Exported and Exporting screens.**
- **Where:** `ExportScreen.kt` → `Progress`, `StatusPill`, `Failed` (the message column), `Result`.
- **Fix:**
  - `Progress`: the row's `clearAndSetSemantics` hides "About 12 s left" from swipe navigation and reads a stale milestone ("25 percent") next to the bar's "42 percent". Split it: a zero-size or invisible live-region node that carries only the milestone announcement and takes no focus, and the "42%" and "About 12 s left" texts left as ordinary nodes.
  - `StatusPill` and the failure message column: a live region on a Row or Column that isn't merged has no text of its own, so what TalkBack announces is up to the TalkBack build. Use `semantics(mergeDescendants = true) { liveRegion = LiveRegionMode.Polite }`.
  - `Result`: it sets both `onClickLabel = label` and `contentDescription = label`, so TalkBack says "Play your video, button, double tap to play your video". Drop `onClickLabel`; the name alone, as the spec says.
- **Spec line:** Accessibility → Exporting, Exported, Failure state.

**P3. The facts line's spoken text carries the dots.**
- **Where:** `ExportSheet.kt` → `FactsLine` (`contentDescription = listOfNotNull(format, estimate).joinToString(". ")`).
- **Fix:** it speaks "MP4 · H.264 · AAC" with the middle dots. At minimum join with `", "` instead of `" · "` (`format.replace(" · ", ", ")`). If TalkBack reads "18 MB" or "20 s" badly on the phone, add the spec's `export_facts_a11y` with units written out. Device check.
- **Spec line:** Accessibility → Sheet; Copy (`export_facts_a11y`).

**P4. The bar and its numbers are 16 dp apart.**
- **Where:** `ExportScreen.kt` → `Progress` (the bar and the percent row are two children of a `spacedBy(space4)` Column).
- **Fix:** wrap them in one `Column(spacedBy(MemixSpacing.space2))`, so the bar and "42%" read as one group.
- **Spec line:** Layout → Exporting screen.

**P5. Copy fixes in four strings.**
- `values-id` `export_done_title` "Selesai" is the same word as the Done button (`export_done`), so the title and the button read the same. Use **"Diekspor"**.
- `values-pt` `export_fail_encoder` is 91 of 90 characters. Use **"Este celular não conseguiu codificar o vídeo nesta configuração. Tente baixar a resolução."** (90).
- `values-id` `export_fail_encoder` says "mengode", which is informal; **"Ponsel ini tidak bisa memproses video dengan pengaturan ini. Coba resolusi lebih rendah."** says it plainly (about 87).
- `values-es` `export_percent` is "%1$d %" with a plain space, which can break before the % sign; use a no-break space (` `).

**P6. The sheet empties while it closes.**
- **Where:** `ExportSheet.kt` → `if (sheet == null) return@Sheet`.
- **The problem:** when `exportSheet` becomes null (Export video, close), the content goes at once and an empty panel slides away over 200 ms, while the Exporting screen pushes in over it. It's brief but it's a visible flash of an empty sheet.
- **Fix:** remember the last non-null `sheet` and draw it until the slide-out ends (`var last by remember { mutableStateOf(sheet) }; if (sheet != null) last = sheet`).
- **Spec line:** Layout → Export sheet (While it closes).

**P7. After Free up space the failure state can't just retry (optional, fine in P1-12b).**
- **Where:** `ExportScreen.kt` → `Failed`, `ExportError.STORAGE_FULL`.
- **The problem:** the user frees space, comes back, and the primary is still "Free up space". The way on is Back to editor, Export, Export video (three taps; the sheet then checks the space exactly), which works and isn't a dead end, but a retry button would be one tap.
- **Fix, if time:** when the app returns to the foreground after the storage screen, the primary becomes **Try again**, and a retry runs the same space check as the sheet (a toast `explain_export_no_space` if it's still short). Not a blocker; I'd do it with P1-12b.

**P8. A frame the user can't judge: Blur shows black on the Exporting frame.**
- Accepted as built (the code draws the first frame without the blur, over black); no change. QA notes whether testers expect the blurred look there. The spec now says the frame uses the canvas color, black for Blur.

## Decisions on the engineer's points
1. **PlayDisc, 56 dp: approved, token added.** `play-disc-size` (56px) is in `design/tokens.json`, `design/system/tokens.json` and DESIGN_SYSTEM → Size, with a new `design/system/components/PlayDisc/README.md`. **Request for the principal mobile engineer (later commit):** add `MemixSize.playDiscSize = 56.dp` in `:core:designsystem` and use it in `PlayDisc.kt` in place of `DISC_SIZE`. No other change: the 24 dp `play` icon in `on-primary` on `primary` stays (7.9:1; the board's 22 px is within rounding). No new color.
2. **`export_res_*` as constants, not strings: confirmed.** "480p", "720p", "1080p", "2K" and "4K" are technical names that never change by language, like "MP4" and "H.264", and the spec already says "Not translated". Two conditions, both met by the build: they live in one place (`ExportResolution.label`) and no screen types its own. The spec's Copy table now lists them as constants. (Screen readers read them fine in all five languages; the frame-rate segments do get a spoken name, `export_fps_a11y`.)
3. **Free up space after a failed export: not the flat 100 MB.** Android treats `EXTRA_REQUESTED_BYTES` as the total the app wants free, so a flat 100 MB is nearly always already satisfied and the system opens a screen that does nothing. Ask for the needed total of the failed choice. The sheet has the same problem with the **missing** amount. See M2 for both, and the spec's new bullet. The engineer's reasoning ("we don't know the exact missing size") is right as far as it goes, and the missing size isn't the right number either; the total is also something the code already knows.
